# Aprendizaje P6 — Integración de las 12 Pantallas React con FastAPI, JWT y SSE

**POR QUÉ**  
El frontend (`apps/web/src/`) funcionaba hasta P5 como un prototipo con datos `INITIAL_*` en memoria, credenciales prellenadas en `Login.tsx`, sesión simulada en `localStorage` (`role: 'admin'`) y mutaciones que no sobrevivían a `F5`. Al conectar las 12 pantallas contra PostgreSQL, JWT real y SSE (`/api/v1/events/stream`), cualquier acción de recepción o administración persiste en base de datos y se sincroniza entre sesiones abiertas sin recargar manualmente.

**QUÉ SE HIZO**  
1. **Cliente HTTP JWT (`apps/web/src/api/client.ts`):** se añadieron `patch()`, `getApiBaseUrl()`, `extractErrorMessage()` y `downloadAuthorizedFile()` para descargar archivos binarios `.xlsx` con cabecera `Authorization: Bearer <token>`, además del evento global `satori:unauthorized` cuando la API responde `401`.
2. **Store real sin mocks (`apps/web/src/store.tsx`):** se eliminaron todos los arreglos `INITIAL_*` y las funciones simuladas. `StoreProvider` carga el perfil desde `GET /api/v1/auth/me`, autentica con `POST /api/v1/auth/login`, cambia contraseña vía `POST /api/v1/auth/change-password`, consulta los recursos reales (`/api/v1/rooms`, `/api/v1/bookings`, `/api/v1/products`, `/api/v1/cafe/menu`, `/api/v1/cafe/orders`, `/api/v1/events`, `/api/v1/expenses`, `/api/v1/finance/summary`, `/api/v1/users`, `/api/v1/audit`, `/api/v1/conversations`) y mantiene sincronización en tiempo real mediante `EventSource` conectado a `/api/v1/events/stream?token=...` (con respaldo de polling cada 15 s).
3. **Pantallas operativas (`Dashboard`, `Rooms`, `CalendarView`, `Reservas`, `Operacion`, `Tienda`, `Restaurante`, `Eventos`, `Chatbot`, `Resenas`, `Login`, `AccountSettingsModal`):** migradas de los números mock `'101'..'303'` a las habitaciones semilla reales `'1'..'9'`, usando mutaciones asíncronas que devuelven `ActionResult` y muestran errores reales de negocio (como colisiones de fechas `409 Conflict` o stock insuficiente).
4. **Gerencia (`apps/web/src/screens/Admin.tsx`):** reemplazados los KPIs ficticios (`19.800.000`, `Semana 1..4`, `Salgados Café 94`) por el resumen real de `/api/v1/finance/summary`, CRUD de egresos, gestión real de usuarios (`username`, rol y estado activo/inactivo), log inmutable de auditoría y descarga real del reporte Excel (`GET /api/v1/reports/export.xlsx`). Además se eliminó el directorio legado `apps/web/src/pages/` (`ReservasDebug.tsx`, `Conversations.tsx`) que apuntaba a rutas debug retiradas en P2.

**CÓMO PROBARLO**  
1. Compilar TypeScript y el bundle de Vite (`tsc && vite build`):  
   ```bash
   cd apps/web && npm run build
   ```
2. Ejecutar las pruebas de backend tras el último cambio:  
   ```bash
   .venv/bin/pytest -v
   ```
3. Con la pila Docker recompilada (`sudo docker compose up -d --build api web`), abrir `http://localhost:5173`, iniciar sesión con usuario y contraseña reales, crear una reserva manual o un cargo de tienda, pulsar `F5` y confirmar que los datos provienen intactos de PostgreSQL.

**PREGUNTAS DE DEFENSA (CON RESPUESTA)**  
1. **¿Por qué `EventSource` envía el JWT como query parameter (`?token=...`) en `/api/v1/events/stream` en lugar de usar la cabecera `Authorization`?**  
   Porque la API estándar `EventSource` del navegador no permite enviar cabeceras HTTP personalizadas (`Authorization: Bearer ...`). El backend valida el token JWT tanto por cabecera como por el parámetro `token` en el stream SSE y cierra la conexión con `401` si es inválido o expiró.
2. **¿Qué garantiza que un usuario Recepcionista no pueda ejecutar acciones administrativas manipulando el frontend?**  
   Aunque el frontend oculta las vistas `a-*` en `App.tsx` y `Admin.tsx`, la seguridad real está en el backend (`require_role("Administrador")` en `apps/api/dependencies/auth.py` aplicado en `expenses`, `finance`, `reports/export.xlsx`, `users` y `audit`). Cualquier petición directa de un token con rol `Recepcionista` recibe `403 Forbidden`.
3. **¿Cómo evita la aplicación perder la sesión o quedar con datos incoherentes si expira el JWT o hay un error en una mutación?**  
   Cuando `client.ts` recibe `401`, limpia el token en `localStorage` y dispara `satori:unauthorized`, devolviendo el usuario a `Login.tsx`. Cuando falla una mutación (por ejemplo, solape de fechas `409` en `EXCLUDE gist`), el `store.tsx` retorna `{ success: false, message }` sin alterar el estado optimista local para que la pantalla muestre el error exacto del servidor.
