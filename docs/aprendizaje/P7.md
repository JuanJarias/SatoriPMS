# Aprendizaje P7 — Flujo n8n V10 (Paridad Wompi sin Redis), Expiración 24h y Canal Web WhatsApp

**POR QUÉ**  
Tras integrar `main` con `migracion-fastapi` en la rama `integracion-fastapi`, coexistían el flujo `V9` (con seguridad `X-Service-Key`, validación de documento titular, cobro Wompi `PENDIENTE_PAGO` y reversión ante fallos, pero dependiente de Redis) y `V10` (sesiones en PostgreSQL pero desactualizado). Además faltaba expiración automática para reservas `PENDIENTE_PAGO` no pagadas, endpoints web de WhatsApp (`toggle-bot`, envío manual) y cierre de exposición de `/api/bookings/debug` en producción.

**QUÉ SE HIZO**  
1. **Paridad completa en `flows/n8n/V10_ChatbotReservas.json` (0 Redis):** reconstruido sobre los 96 nodos y conexiones de `V9` reemplazando los 7 nodos Redis (`session:*` y `wompi:link:*`) por peticiones HTTP autenticadas con `X-Service-Key` hacia `/api/v1/conversations/session/{key}`. Retirado `redis` de `docker-compose.yml` y actualizados `scripts/` y `tests/chatbot/` (`lib/env.js`, `verify_n8n_flow_integrity.py`, `suite_pruebas_chatbot.js`, `test_pago_wompi_v9.js`, `test_e2e_*.js`).
2. **Expiración de `PENDIENTE_PAGO` (24 h):** [n8n_compat.py](../../apps/api/routers/n8n_compat.py) asigna `expires_at = NOW() + 24 h` a las reservas `PENDIENTE_PAGO` del chatbot; [expiration_service.py](../../apps/api/services/expiration_service.py), [booking_service.py](../../apps/api/services/booking_service.py) y [room_service.py](../../apps/api/services/room_service.py) expiran y liberan automáticamente habitaciones con `PENDIENTE_PAGO` vencido.
3. **Endpoints WhatsApp web + restricción debug:** [conversations.py](../../apps/api/routers/conversations.py) añade `GET /api/v1/conversations/session-keys`, `POST /api/v1/conversations/{id}/toggle-bot`, `POST /api/v1/conversations/{id}/messages` y filtra `session:%` en la bandeja; [store.tsx](../../apps/web/src/store.tsx) y [Chatbot.tsx](../../apps/web/src/screens/Chatbot.tsx) permiten alternar Bot/Humano y enviar respuestas manuales; `GET /api/bookings/debug` queda restringido a `X-Service-Key`/`Administrador` y responde `404` cuando `ENVIRONMENT=production`.
4. **Limpieza documental y archivos residuales:** retirados duplicados de Actividad 5 en raíz y `docs/Presentaciones/`, código Java residual `apps/api/src/`, planes de limpieza ejecutados y `docs/legacy-ref/`; actualizado [AGENTS.md](../../AGENTS.md) para la arquitectura integrada.

**PREGUNTAS DE DEFENSA (CON RESPUESTA)**  
1. **¿Cómo evita `V10` necesitar Redis para enlaces de Wompi y ventanas de inactividad de 10 minutos?**  
   Usando la misma tabla `conversation` de PostgreSQL 16 mediante `/api/v1/conversations/session/{key}` con `expires_at` por TTL (`660 s` para sesiones y `86400 s` para `wompi:link:*`), autenticada con `X-Service-Key` y filtrada en la bandeja web por prefijo `session:%`.
2. **¿Qué pasa si un huésped genera un enlace de Wompi desde WhatsApp pero nunca paga?**  
   La reserva nace en `PENDIENTE_PAGO` con `expires_at = NOW() + 24 h` bloqueando solapes bajo `EXCLUDE USING gist`; pasadas las 24 h sin confirmación del webhook, `APScheduler` (o la consulta de disponibilidad en línea) la marca `EXPIRADA` y libera la habitación.
3. **¿Cómo se protege `GET /api/bookings/debug` sin romper la suite de pruebas del chatbot?**  
   Exige `X-Service-Key` o rol `Administrador` (ya no `Recepcionista`, devolviendo `403`) y retorna `404` automáticamente cuando `ENVIRONMENT=production`.
