# Lote P4 — Scheduler 60 s (`APScheduler`), Puerto Wompi Sandbox y SSE Tiempo Real (`HU-03`)

## 1. Qué hace
- Incorpora `apscheduler` en [requirements.txt](../../apps/api/requirements.txt) y configura el ciclo de vida `lifespan` en [main.py](../../apps/api/main.py) para ejecutar cada 60 s el job [expire_stale_booking_locks](../../apps/api/services/expiration_service.py), marcando bloqueos `BLOQUEADA_TEMPORAL` vencidos como `EXPIRADA`, registrando auditoría inmutable y notificando opcionalmente al webhook de n8n (`N8N_EXPIRED_WEBHOOK_URL`) con `X-Service-Key`.
- Implementa el bus de eventos en proceso [event_bus.py](../../apps/api/services/event_bus.py) y el endpoint SSE autenticado `GET /api/v1/events/stream` en [events_stream.py](../../apps/api/routers/events_stream.py) para sincronización en tiempo real del calendario y tablero web (`HU-03`).
- Refactoriza [payment_service.py](../../apps/api/services/payment_service.py) y [payments.py](../../apps/api/routers/payments.py) con el puerto hexagonal `PaymentGatewayPort` (`SandboxPaymentGateway` y `WompiPaymentGateway`), soporte de `POST /api/v1/payments/checkout-link` y validación de `X-Hub-Signature-256` (HMAC) y `X-Event-Checksum` oficial de eventos Wompi `transaction.updated`.

## 2. Por qué así
- La expiración inline durante `GET /availability` y `POST /lock` protege contra sobreventa, pero un bloqueo abandonado en WhatsApp también debe liberarse proactivamente a los 15 minutos aunque ningún otro huésped consulte esa habitación (`APScheduler` cada 60 s).
- El puerto `PaymentGatewayPort` desacopla la lógica de reservas respecto de la pasarela concreta, permitiendo pruebas deterministas en sandbox y conexión real a Wompi sin cambiar los casos de uso.
- SSE (`text/event-stream`) sobre HTTP estándar evita la complejidad de mantener un broker WebSocket externo manteniendo actualización instantánea entre recepción y administración.

## 3. Cómo probarlo
```bash
.venv/bin/pytest -v
cd apps/web && npm run build
```

## 4. Tres preguntas de defensa
1. **¿Por qué usan `APScheduler` en proceso en lugar de Celery + Redis?**
   > Porque el stack prohíbe Redis y para un hotel de 9 habitaciones (~40 reservas/mes) un job asíncrono ligero dentro del `lifespan` de FastAPI evita infraestructuras pesadas manteniendo consistencia transaccional directa sobre PostgreSQL 16.
2. **¿Cómo garantizan que el navegador pueda abrir `EventSource` si el endpoint SSE exige JWT?**
   > `GET /api/v1/events/stream` acepta JWT tanto por cabecera `Authorization: Bearer` como por query `?token=` y lo valida con `get_current_user` contra `system_users` antes de suscribir la cola del cliente.
3. **¿Cómo valida el backend los webhooks de Wompi y previene cobros duplicados?**
   > Verifica en tiempo constante la firma HMAC `X-Hub-Signature-256` o el checksum SHA-256 de Wompi (`propiedades + timestamp + WOMPI_EVENTS_SECRET`), y verifica unicidad de `Booking.payment_id` en PostgreSQL para retornar `already_processed` de forma idempotente.
